# Decision Audit: Issue #6 (Game control buttons do not respond to real clicks)

## Agent A: Model Chooser
**Timestamp:** 2026-07-29 15:46 PDT
**Decision:** opus
**Rationale:** src/ui/main.ts's render() (lines 30-52) does a single `app.innerHTML = ...` replace of the entire control surface, and the driver's setInterval loop (lines 111-140, DRIVER_INTERVAL_MS=100) can invoke it up to 10x/second while unpaused, plus click handlers and the spacebar handler each call render() again on top of that. render.ts confirms nearly everything -- stats, loop diagrams, stall banner, time controls, decisions/projects, choices, log -- is generated as fresh HTML strings on every call, with no existing notion of partial/subtree updates. A correct fix is not a one-line "skip render if unchanged" patch: it requires restructuring render() into independently-updatable pieces (or introducing DOM diffing) so interactive nodes like #pause and .tc-btn keep stable identity across ticks, while continuing to update fast-changing subtrees (stats, log) every tick. That restructuring has to preserve several behaviors it currently gets "for free" from the blow-it-all-away model: data-buy/data-project/data-choice/data-option delegation reading fresh dataset attributes off #app (main.ts lines 55-104), the driver's per-tick render() cadence and autosave-on-day%10 check (lines 131-137), and the event-driven save-on-action tail. There is no existing test file for main.ts's render loop or click delegation (only render.test.ts, which covers the pure render.ts template functions in isolation) -- so there's no safety net catching a regression in click handling or a stale-DOM bug introduced by whatever targeted-update mechanism is chosen. Given the real architectural choice involved (diff library vs. hand-rolled subtree splitting), the multiple interacting behaviors that must not regress, and the lack of test coverage for exactly the surface being changed, this warrants the most capable model.
**Handoff to Agent B:** Prefer the "restructure render() into independently-updatable subtree functions that skip DOM replacement for regions whose relevant state hasn't changed since last render (time-controls in particular, keyed on paused+speed)" direction over pulling in a generic vdom-diff dependency, since it's the smaller footprint that still fixes the root cause (interactive nodes stop being torn down every tick) without touching the data-* delegation pattern in main.ts's click handler; also add a test around main.ts's render/click loop (currently absent) that would have caught this class of bug, e.g. asserting the #pause node's identity (or at least its listener behavior) survives across repeated render() calls with unpaused state.

**What could go wrong:**
- Worst case: a memoized region goes stale, so the DOM silently disagrees with game state -- a Buy button that stays enabled after the budget drops, or a countdown frozen at the wrong day. That is worse than the bug being fixed, because it misleads rather than merely ignores input. It can only happen if a region's html string fails to capture something its display depends on, which is why every section's html is recomputed from state on every render and only the write is skipped; nothing is conditionally recomputed.
- Blast radius: the whole visible control surface, single-player and client-side only. No engine, save-format, or content changes (src/engine is untouched, and the purity test still passes), so nothing can corrupt a save.
- Likelihood: low. The memo key is the full html string for the region, so any change to any rendered value already invalidates it. Five tests specifically assert freshness in the opposite direction (label flips, active speed marker moves, purchase appears in Owned, resolved choice disappears, new log line appears). The residual risk sits in the two hand-split regions, where a future edit could put a volatile value into a scaffold that is only rewritten on set changes.
- Mitigation: the split points are commented in render.ts with the reason; renderProjectOffers has a test asserting its string does not change as in-flight work progresses, and renderChoicesScaffold has one asserting it is stable across days -- either would fail loudly if a volatile value were moved into a stable block. Rollback is a single revert: the mechanism is three files and no dependency (jsdom is devDependencies only). If a staleness bug ever did appear in the field, a one-line escape hatch (always write, never memo) restores the old behavior.
- Note: jsdom was added as a devDependency because the project had no DOM test environment; it is scoped to the two new test files via a per-file @vitest-environment docblock, so the existing node-environment tests are untouched.
