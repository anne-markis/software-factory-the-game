## Agent A: Model Chooser
**Timestamp:** 2026-07-29
**Decision:** sonnet
**Rationale:** chargeUpkeep (src/engine/tick.ts:39-64) is a single, well-isolated function with one call site (tick(), line 125), and incomePerDay is only ever read in this one place plus a UI display formatter (src/ui/effectSummary.ts) that has no economic effect — so the blast radius of a fix is small. The fix direction from the issue is clear (net burn against income before clamping to 0), but real judgment is needed: the existing code has a deliberate two-pass structure (credit all income, then charge all payroll) explicitly commented as intentional so a later-purchased decision's income can rescue an earlier decision's payroll regardless of purchase order, and the fix must preserve that invariant while changing only the burn-clamp interaction. tick.test.ts has no existing test that exercises incomePerDay or the insolvency/payroll-rescue interaction directly, only a burn+revenue arithmetic test (lines 46-53, asserting exact budget values like `10000 - 60 + 17`), so a correct fix must reason carefully about ordering to avoid silently breaking that assertion or the payroll-rescue behavior. This is well-scoped, single-function, non-architectural work, but the economic-balance judgment and the need to reconcile two documented design invariants push it above a purely mechanical haiku-level change.
**Handoff to Agent B:** Preserve the "credit all income before charging any payroll" ordering and the "budget never goes negative" design invariant (both explicitly commented in chargeUpkeep) while netting baseBurnPerDay against total incomePerDay in the same step before the clamp to 0, and verify against tick.test.ts's existing burn/revenue arithmetic test (lines 46-53) plus add a new test for the insolvency-income scenario described in the issue.
