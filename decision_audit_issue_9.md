# Decision Audit: Issue #9 (Points/Day stat does not match the rate shown in the diagrams)

## Agent A: Model Chooser
**Timestamp:** 2026-07-29 14:56 PDT
**Decision:** sonnet
**Rationale:** The root cause is already confirmed and precisely located (tick.ts computes shippedFlow/finishFlow as capped, realized per-stage flow, but only shippedFlow is persisted as state.pointsPerDay, while loopDiagram.ts's arrow labels and inProgressPanel.ts's exit box both call effectiveRate for "deploy"/"finish" directly, which is uncapped capacity). At the same time the issue itself lays out both fix directions clearly with a well-understood root cause, so this isn't ambiguous/architectural enough to need opus -- it's a well-scoped, moderate multi-file change with some judgment calls, which is squarely sonnet's territory.
**Handoff to Agent B:** Lean toward direction (a) for the deploy/finish arrows and exit box (thread realized flow, mirroring pointsPerDay, likely via a small new state field like state.finishFlow set in tick.ts) since it fixes the actual reported confusion rather than just re-labeling it, but note the "pull" arrow in loopDiagram.ts has no discrepancy today (Backlog isn't capacity-capped independently the way Done/In Progress are) so only the finish/deploy arrows and the exit box need the realized-flow treatment; also update the existing exact-string assertions in loopDiagram.test.ts and inProgressPanel.test.ts (e.g. the "1.0/day" / "Base 1.0/day" / "= outer loop throughput" checks) to match whatever new values or labels are chosen, and double-check behavior on a fresh game's first tick (done/inProgress both 0) as called out in the issue's repro.
